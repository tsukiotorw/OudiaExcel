## 4. 今後の機能移植順序

残る5項目を、以下の順序で実装する。

### 第1グループ：上下段レイアウト

以下の3項目をセットで進める。

1. 行先・列車種別の上下段配置
2. 同じ段に配置された項目の表示順序
3. 上段・下段それぞれの高さ

これらは互いに関連するため、まとめて仕様を整理し、一体として設計・実装する。

Windows版の表示仕様を確認したうえで、Web版へ移植する。

### 第2グループ：時刻欄の中央配置

第1グループの完了後に実施する。

時刻欄の表示位置・配置をWindows版と同じ仕様にする。

### 第3グループ：列車欄の幅

最後に実施する。

上下段のレイアウトや時刻欄の配置が確定した後、列車欄の幅を調整できるようにする。

## 5. 表示設定UIの改善

今回の機能移植に加えて、表示設定UIの改善を行う。

### 5-1. 基本方針

現在の表示設定UIを、設定項目ごとのタブ形式に変更する。

設定項目が増えても目的の設定を見つけやすく、操作しやすい構成を目指す。

### 5-2. タブの分類

具体的なタブの分類・名称は、現在の設定項目を整理したうえで決定する。

現時点では確定していない。

### 5-3. 維持する機能

UI変更後も、以下の機能を維持する。

- 設定値の保存
- 設定値の復元
- プレビューへの即時反映
- Excel出力への反映
- 既存設定との整合性

単に画面をタブ化するだけでなく、設定変更からプレビュー、Excel出力まで一貫して動作することを確認する。

## 6. 開発の進め方

### 6-1. 変更前の調査

機能移植を始める前に、必ず以下を確認する。

- Windows版の該当機能の実装
- Windows版での設定値・データの持ち方
- Web版の現在の実装
- 関連する関数・メソッド・クラス
- プレビューとExcel出力へのデータの流れ

既存コードを確認せずに、関数名や属性名を推測して実装しない。

### 6-2. 段階的な実装

- 変更範囲は必要最小限にする。
- 一度に大量のコードを変更しない。
- 原則として小さな変更単位で実装・テスト・確認する。
- 変更案を提示した後は、ユーザーによる適用と動作確認を待つ。
- 確認が完了する前に次の変更へ進まない。

### 6-3. テスト・動作確認

コード変更後は関連するpytestを実行する。

可能な限り全テストも実行する。

以下の状態を区別して管理する。

- 実装済み：コードへの実装が確認できている。
- テスト済み：pytest等による検証が成功している。
- 動作確認済み：実際の画面やExcel出力を確認している。
- 未確認：実際の動作や結果をまだ確認していない。
- 未実装：まだ実装されていない。

pytestの成功だけで、画面表示やExcel出力が正常であると判断しない。

### 6-4. コード変更案の提示

コード変更を提案する場合は、以下を明示する。

1. 対象ファイルのパス
2. 対象クラス・関数・メソッド名
3. VSCodeで検索できる既存コードやコメントなどの目印
4. 追加・置換・削除するコード
5. 変更後の前後関係が分かるコード例
6. 変更理由と他の機能への影響

### 6-5. GitHub運用

- GitHubのmainブランチをソースコードの正本とする。
- 作業開始前に最新状態を確認する。
- 作業終了後はテスト結果を確認する。
- ユーザーの明示的な許可なくコミット・プッシュしない。
- 既存の変更や未コミットのコードを無断で破棄しない。
